# 更新日志（Changelog）

> 版本遵循语义化 `MAJOR.MINOR.PATCH`（规则见「版本概念」）：破坏性改动动 `MAJOR`、新增能力动

- **v1.7.8（当前）**：**全技能优化审视（用户要求「整体，把技能优化审视一遍」）**。
  流程：先通读 4 脚本（约 2700 行）+ 4 篇文档 → 做**静态测量**（AST 未用 import / 复杂度 /
  死定义 / 参数面一致性）与**运行时微基准** → 按数据定清单（含**放弃项**）→ 逐项改 → 逐项回归。
  动 `make_map.py`（主）、`download_imagery.py`、`satellite_imagery_cn.py`。

  - **(A) 出图性能：先量出瓶颈，再动手**。阶段分解（包河区 z17 / `--max-side 2600 --dpi 200`）：
    `load_display_array` **1428 ms（56%）** / `_render_map_core` **50 ms（2%）** /
    `savefig` **1080 ms（42%）**。**装饰件只占 2%** —— 所以本轮完全没有改版式代码，
    只优化两个大头：
    1. **降采样读的重采样核 `bilinear` → `average`**：1420 → **1004 ms（1.41×）**。
       这一跳是 23943px 源 → 4848px（约 4.9×）的**降采样**，bilinear 只取 2×2 邻域、
       不覆盖像元足迹，必然混叠；average（面积平均）才是正确核 —— 属「更快且更对」。
       与旧产物像素差 mean 0.31 / p99 2 / max 7（/255）。**只改这一跳**，随后 reproject
       到目标网格那一跳（跨 CRS 重投影）保持 bilinear。
    2. **PNG 存盘 zlib 级别 6 → 3**（`PNG_COMPRESS_LEVEL`）：1123 → **1002 ms（1.21×）**，
       **体积完全不变（18.56 MB）、产物逐像素差 0**。不再降到 1（再快 9% 但体积 +25%）。
    - 端到端：同参数 **2.8 s → 2.2 s（约 −21%）**；同参数产物逐像素差 mean 0.243 / p99 2，
      差异>2 的像素仅 0.303%（全部来自新的 average 核）。
    - **放弃项（均有实测）**：GCJ-02 向量化（包河区仅 **282 顶点**，省 0.45 ms）·
      `WarpedVRT` 直读（**7018 ms**，比现路径慢 4.8× 且网格算错）· 装饰件优化（占 2%）·
      继续降 PNG 级别（体积 +25%）· 把 `--supersample` 默认降到 1.0（读图快 3.2× 但改变
      所有产物观感，属默认行为变更，不擅自改）· 拆分 `build_mosaic`（188 行/38 分支，
      收益仅可读性而回归风险高）。
  - **(B) 上一轮（v1.7.7）遗留的自相矛盾代码**：`make_map.py` / `satellite_imagery_cn.py`
    里 `os.environ["PYTHONDONTWRITEBYTECODE"] = "1"` 仍**在行**，而它紧邻的注释正是

    `sys.dont_write_bytecode = True`）。已删除。

    硬编码 `["esri","google"]`，而 `download_imagery` 用的是 `list(SOURCES.keys())` ——
    给 `SOURCES` 加第三个源时，一键入口会不认。现两者同源。

    `default=None` + 运行时取 `make_map.DEFAULT_MAP_DPI` / `DEFAULT_MAX_SIDE`

  - **(E) 报数与实际不符**：`feather_mosaic` 打印的理论缝数 `nx-1` / `ny-1`，在

- **v1.7.7**：**全技能审视（用户要求「整体审视一下技能，修复 bug」）—— 出图版式
  随图幅脱钩的 4 处缺陷 + 2 处一致性缺陷**。动 `make_map.py`（主要）、`download_imagery.py`、

  - **(A) 图例文字溢出面板（用户可见，轴宽 <7 in 必然发生）**。图例框写死 `axes 0.27 × 0.056`，
    框内文字却是固定磅值（9.5 / 8.8 pt）—— 二者随图幅长宽脱钩。实测（探针，非估算）：
    轴宽 8.76 in 时余量 0（临界）、6.80 in 溢出 0.09 in、**5.30 in 溢出 0.14 in、3.40 in 溢出
    0.68 in**；`--max-side 900 --map-dpi 150` 这种小图即可复现，图上表现为区县名跑到白框外。
    **改法**：图例版式常量改为**英寸**（按 `LEGEND_REF_AX_W_IN = 10.3` 基准标定，逐点复现旧值

  - **(B) 数据来源注记写死 Esri**。`_draw_title_and_credit` 硬编码「数据来源：Esri World

    从血缘标签取源名并去掉括注（`Google Satellite (需代理/境外)` → `Google Satellite`）。
  - **(C) 标题栈可能被图幅上沿静默裁切**。上边距写死 `TOP_IN = 0.5 in`，标题栈高度却按估算
    行高定位：`img_w_in ≥ 31 in`（如 `--max-side 3500 --dpi 100`）时字号到 14 pt，加副标题
    需 `0.12 + 0.263 + 0.175 = 0.558 in > 0.5 in`，副标题少了半行字。改为 `_title_layout()`
    按保守行高算出所需边距取 `max(0.5in, 需要值)`，并新增 `_fit_text_fs()` 实测收字
    （步长 0.5 pt、下限 6 pt）防标题横向溢出。验证 8 组图幅×2 种标题长度（含 34 字长标题、
    35in 大图、1.5in 极小图）全部 `top ≤ 1.0`、标题不越图宽。
  - **(D) 下载器「全部瓦片失败」判据不可达**。`build_mosaic` 的 `if n_fail == n` 永假 ——
    首张瓦片由「源可达性探测」取回、失败即 `SystemExit`，故 `n_fail` 最多 `n-1`，
    「产物是占位灰图」的提示从未打印过。改为按**真正拿到统计结果的瓦片数** `n_ok` 判断，
    并单列「除首张探测瓦片外全部失败」的严重告警（含填充色值）。桩 session 回归：
    11/12 失败时正确打印告警、全成功时不打印。

- **v1.7.6**：**比例尺卡片几何改为「实测包围盒」反推**（用户再次反馈「比例尺怎么超出了
  背景卡片」）。仅动 `make_map.py` 的 `_draw_scale_bar()` + 新增三个工具函数。

  - **背景**：v1.7.4/v1.7.5 的卡片矩形是「按字号估算反推」—— `0.62em × 最宽标签字数 ÷ 2 + pad`。
    那是个**粗估上限**，字体/字宽一变就不再可靠；且当 `SCALE_BAR_X0 - pad_x < 0` 时矩形左沿被
    `max(0.0, ...)` 夹到 0，卡片被图幅边界裁掉，内容就会露在卡片外。
  - **改法（权威来源）**：先把条带、刻度线、标注文字**全部画出来**，再用它们的
    `get_window_extent(renderer)` **实测渲染包围盒并集** + `PANEL_PAD_PT` 留白得到卡片矩形
    （`_artists_bbox_axes()`）；文字宽度也用真实字体实测（`_measure_max_half_width_pt()`），
    不再用 `0.62em` 估算。新增 `_get_renderer()` 统一取 Agg renderer。
  - **窄图幅兜底**：`_scale_bar_geom()` 增加 `target` 参数；若「条带 + 两侧留白」塞不进图幅水平
    空间，先把条带右移（`x0f = max(SCALE_BAR_X0, pad_x)`），仍不够则按
    `_SB_SHRINK_TARGETS` = 0.18→0.16→…→0.06 依次缩短目标长度，最多迭代 3 轮（缩短会改变标注
    宽度）。避免卡片被坐标轴裁掉后内容外露。
  - **回归验证**：新增「6 图幅 × 4 图形尺寸 = 24 组合」测试，逐组断言
    ① 卡片包住全部图元 ② 卡片落在图幅内 ③ 条带外框宽 = 各分段宽之和 —— **24/24 通过**
    （含长条形 1:6、极小图幅、2in 窄图、49.6°N / 18.3°N 高低温差）。
  - **包河区 z17 / 300 DPI 实图复核**：卡片实测 axes x 0.0259–0.2611（灰边 #8c8c8c 定位），
    条带外框 0.0395–0.2456 → 左右余量 42 px / 48 px，刻度与标注均在卡片内。

- **v1.7.5**：**修复比例尺条带外框越界**（用户反馈「这比例尺有问题，怎么突出来了」）。
  仅动 `make_map.py` 的 `_draw_scale_bar()`，是 v1.7.4 重构时引入的回归。

  - **症状**：黑白分段、刻度数字、白色面板都正常，但**整条白色衬底 + 黑色外框向右拖出去
    一大截**，穿过面板边界伸到图幅中部。
  - **根因**：条带用 `blended_transform_factory(ax.transData, ax.transAxes)` 绘制 —— x 是**数据
    坐标**，`Rectangle(..., width, ...)` 的 `width` 必须是**经度差** `width_deg`（包河区
    0.052702°）。v1.7.4 重构时把外框与白衬两处的宽度误写成 `width_frac`（axes 分数 0.20517），
    二者相差 `(east-west)` 倍：本图幅 0.256869° → **3.9×** 错误，外框被画成 0.206 **度**
    ≈ **19.5 km**（应 5 km）。
  - **为什么难发现**：分段 `seg_w = width_deg/nseg`、刻度线、标注文字、面板矩形用的都是**正确
    单位**，所以黑白块端点 / 数字 / 面板全都对得上；只有首尾两个矩形错。v1.7.4 的「实测验证」
    只量了黑色分段（0.0802–0.1223 / 0.1624–0.2045）与面板右沿，恰好绕开了外框 —— 属于典型
    **测量选点偏差导致的假通过**。
  - **修复**：显式区分两个量并注明单位 —— `width_frac`（仅面板块，axes 分数）、
    `bar_w = geom["width_deg"]`（条带本体，数据空间），外框与白衬改用 `bar_w`。
  - **回归验证（包河区 z17，300 DPI）**：① 逐行扫描，**越界白条行数 = 0**（修复前该白条从
    0.246 一直延伸到约 0.84 处）；② 条带 5 段刻度落在 axes x 0.0400 / 0.0810 / 0.1221 /
    0.1631 / 0.2041 / 0.2452（等分，步长 0.0410）；③ 面板右沿 0.2618 = 条带右沿 0.2452 +
    pad 0.0166，条带完全在面板内；④ 截图目视确认外框与末刻度齐平，无任何伸出。

    - **新实现**：`N = a/√(1−e²sin²φ)`（卯酉圈曲率半径），`米/度 = N·cosφ·π/180`，
      并在**尺子自身纬度**上计算。包河区实测偏差 **±0.000%**（5000.0 m vs 标称 5000 m）。
    - **可读性**：总长取漂亮数后再选能整除成漂亮数的**最大段数**（5→4→3→2），
      包河区得到 `5 km ÷ 5 = 1 km/段`，刻度 0/1/2/3/4/5 km 逐一刻度居中标注
      （旧版只有 0 与全长、且首尾用 `ha=right/left` 贴边，视觉上尺子比标称值长/短）；
      黑白**交替分段**（ArcGIS Alternating Scale Bar 风格）；标注密度按尺长点数自适应
      （`<26 pt/段` 退化为仅首尾，`<42 pt` 仅全长）。
    - 常量集中为 `SCALE_BAR_X0/Y0/H/TARGET`，`_scale_bar_geom()` 同时供绘制与预留区计算复用。

  - **(B) 图例自动避让，不再压研究区区界线**（`_place_legend` / `_legend_anchor` /
    `_boundary_pressure` / `_seg_rect_hit` / `_normalize_rings` / `_draw_boundary_rings`）。
    - **根因**：旧版图例硬编码右下角 `(1-bw-0.025, 0.03)`。区界形状因区县而异，包河区区界
      正好**斜穿右下角**，红线直接压在图例框上（实测框内区界顶点 1 个、横穿 1 段）。
    - **修法**：8 个语义锚点（`se/sw/ne/nw/e/w/s/n`）逐一评分：
      `代价 = 区界压力×1000 + 与预留区重叠面积×100`。区界压力 = 框内顶点数（含 0.004 边距）
      + Liang–Barsky 判定为「直接穿框」的分段数（兜住稀疏边界无顶点落框的情形）；
      预留区 = 比例尺（`_scale_bar_reserved`）+ 指北针（`_north_arrow_reserved`）。
      同分按 `se → sw → ne → nw → e → w → s → n` 取靠前者，**右下优先的 ArcGIS 观感得以保留**。
      全部候选都有冲突时取最小代价并提高不透明度到 0.94。
    - **复验**：包河区锚点评分 SE=1000（区界压力 1）/ SW=1.15（压比例尺）/

  根因：`_crop_to_bbox` 调 `from_bounds(new_left, new_top, …)` 时把 `new_top`（北边界）当成了 `bottom`、
  把 `new_top - new_h*res`（南边界）当成了 `top`。`from_bounds(left, bottom, right, top, w, h)` 第 2/4
  参数写反后，输出 Affine 的 `e` 由 **−res 变成 +res**（row 0 被声明为最南），于是**像元数据是对的、
  地理参考却上下颠倒**。此 bug 为**历史遗留**（非 v1.5.0 引入），与 v1.5.0 的三处叠加放大错位。
  - **性质区分**：v1.5.0 修的是「像元位置错」（请求到别的半球 + 行序镜像）；本处修的是「像元对、
    坐标声明错」（GIS 与按坐标取样会取到镜像像素，但缩略图/直读看起来正常，最易漏检）。
  - **验证（变换无关法，测量优先）**：用独立获取的 Esri 底图（`flip=False`，已验证与实景一致）在同一
    bbox 建参考，与 TIF 像元**直接比较**：正向 **NCC = 0.937**，垂直翻转仅 **0.005**（相差 4 个数量级）
    —— 证明像元网格确为 north-up，问题只在 geotransform。修复后 `e < 0`、北边界纬度 = 32.061（原 31.818）。
  - **附带修复（CLI）**：`satellite_imagery_cn.py` 与 `make_map.py` 的 `ArgumentParser` 增加
    `allow_abbrev=False`，并给一键入口补上真正的 `--boundary` 选项。此前仅存在 `--boundary-color`，
    命令行写 `--boundary <json>` 会被 argparse 的前缀缩写匹配成 `--boundary-color <json>`，
    把 JSON 路径当颜色值 → 出图 `ValueError` 崩溃。现已显式支持 `--boundary`（路径/JSON 串）。
- **v1.5.0**：**严重正确性修复**（影像与其地理参考完全错位，共三处根因）+ **新增研究区边界叠加**。
  这是本 skill 最难察觉的一类 bug：经纬网来自 TIF 自身 geotransform，因此专题图上的经纬度标注
  看起来完全正常，而实际影像却是错的（例如「瑶海区」被画成了西澳小麦带的农田）。

  - **(A) 根因 3（上下各错 1 个瓦片）**：整块地理范围用 `mercantile.ul((x0,y1))` / `ul((x1+1,y0-1))`
    计算。改用角瓦片 `xy_bounds(Tile(x0,y0))`（左/上）与 `xy_bounds(Tile(x1,y1))`（右/下）。
  - **验证（测量优先）**：把四个「URL 翻转 × 行偏移」组合的拼接结果与独立获取的 `flip=False`

    27~40 灰度级；再用瓦片中心点回算经纬度，误差 **0.00000**（修复前 0.245°，约 27 km）。

    清空缓存**（`--clean-cache`，或手动删除 `_tiles/`）再下载，否则会复用错误瓦片。
